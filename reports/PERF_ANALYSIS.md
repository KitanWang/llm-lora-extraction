# 7B 训练吞吐分析：micro-batch 计时与 step 换算

**结论：4.0 s/micro-batch 是本机（RTX 5060 Laptop 8GB）的正常速度，不存在性能故障。**

本文记录一次「疑似性能退化」的定位过程，以及一个被证伪的优化假设。

---

## 1. 现象

7B QLoRA 训练的进度条显示约 64 s/step，而早期压力测试脚本
（`scripts/sweep_train_config.py`）报告 1.88 s/micro-batch，
乘以梯度累积 16 后应约 30 s/step —— 相差 2.1 倍。

## 2. 排查

### 2.1 先排除的假设

| 假设 | 验证方式 | 结论 |
| :--- | :--- | :--- |
| 样本长度变了 | 统计新旧数据集 token 长度 | 排除（652 vs 667，基本一致） |
| 数据集版本问题 | 对比两次训练的数据来源 | 排除 |
| 与其他任务争抢 GPU | `nvidia-smi` 观察 | 训练期间无并发任务时仍慢 |

### 2.2 对照实验：显存分配器

怀疑高显存占用（7550/8151 MiB，94%）下 native 分配器碎片化，
测试 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`。

**同进程对照（模型只加载一次，避免加载开销干扰计时）：**

| 配置 | s/micro-batch | 峰值显存 |
| :--- | ---: | ---: |
| 默认分配器 | **4.03** | 6.05 GiB |
| `expandable_segments:True` | 4.63 | 6.04 GiB |

→ **该优化无收益（反而慢 15%），不采用。**

### 2.3 真正的根因

这次对照实验给出了关键数字：**基线就是 4.03 s/micro-batch**。
换算到训练进度条：

```
4.03 s/micro-batch × 16 (gradient_accumulation_steps) ≈ 64.5 s/step
```

与实测 63.5~64.3 s/step **完全吻合**。

也就是说，**训练速度一直是正常的，是早期的压力测试脚本测错了**：

1. 该脚本把 8 条样本编成 **1 个 batch** 计时，而生产配置是 `bs=1`；
2. 只丢弃了第 0 步，但 batch 变化时 cuBLAS 的内核选择与显存池预热并未完成。

修正脚本后（`--micro-batch` 参数 + 预热步排除），基线与训练完全一致。

## 3. 关于「后期速度退化到 165 s/step」

训练进入 epoch 1 后期曾出现 64 → 165 s/step 的退化。原因是**外部干扰**：

- 同一张 GPU 上并发跑了评测验证脚本（5 条推理）；
- 显存余量被压到 <100 MiB，触发 WSL 显存超售（溢出到主机内存）。

干扰移除后速度即回落。**这不是训练本身的问题**，
但说明本机（8 GiB，实际可用 6.87 GiB）上 **GPU 任务必须串行执行**——
这也是 `scripts/run_all_experiments.sh` 强制串行的原因。

## 4. 实际耗时

7B / 200 步 / `bs=1` / `grad_accum=16` / `seq_len=832`：
约 64 s/step × 200 ≈ **3.5 小时**（含 epoch 边界的验证开销）。

## 5. 经验

**性能结论必须在「无并发 + 预热充分」的条件下取得**，否则容易把测量噪声当成结论。
本次先后产生过两个错误判断：

1. 「实际训练比压测慢 2.1 倍」——实为压测脚本的 batch 组织与预热问题；
2. 「`expandable_segments` 可提速」——实测反而更慢。

两次都是通过**同进程对照实验 + 与生产进度条交叉验证**才发现并纠正的。
