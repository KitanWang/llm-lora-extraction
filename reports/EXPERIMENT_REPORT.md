# 实验报告：中文采购询价结构化抽取的 LoRA / QLoRA 微调

> 所有数字均为本机实测，可复现：数据构建、训练、评测、报告生成各有独立入口（见 README）。

---

## 一、实验目的

验证「在消费级显卡上做垂直任务微调」这条路径是否成立，具体到三个子问题：

1. **怎么做数据**——从零构造一套有区分度的中文抽取数据集，而不是找现成数据集跑一遍；
2. **怎么做训练**——在**单张 8 GB 消费级显卡**上完成 LoRA 与 QLoRA 微调；
3. **怎么量收益**——用微调前后对比证明「微调真的有用」，且能说清提升来自哪里。

## 三、数据集

### 3.1 任务与难点

输入一段中文 B2B 采购询价文本，输出 9 字段固定 JSON。**难点是刻意设计的**：

| 难点 | 具体表现 | 考察能力 |
| :--- | :--- | :--- |
| 多实体混淆 | 正文同时出现**收件方**、**客户**、**第三方**公司名 | 角色识别 |
| 型号 vs 单号 | `HX-1234`（型号）与 `PO20250315-07`（订单号）形似 | 语义区分 |
| 中文数量词 | 「1.2万台」「3千件」→ 整数 | 语言理解 + 归一化 |
| 只给总价 | 有总价无单价 → **必须输出 null** | **抑制幻觉** |
| 相对日期 | 「发件日期 3/15，希望 30 天内交货」→ `2025-04-14` | 多步推理 |
| 口语付款条件 | 「先打三成定金，货到再付七成」→ 枚举值 | 表达归一化 |
| 否定陷阱 | 「不着急」「非加急」→ `is_urgent: false` | 否定语义 |
| 干扰号码 | 传真号、总机分机 vs 手机号 | 细粒度区分 |

### 3.2 规模与清洗（pandas）

合成 3628 条 → 清洗后 **3000 条**，漏斗如下：

| 步骤 | 剩余 | 淘汰 | 规则说明 |
| :--- | ---: | ---: | :--- |
| 原始合成 | 3628 | — | 已含刻意注入的脏数据 |
| 非空正文 | 3628 | 0 | |
| 型号在正文中 | 3628 | 0 | 型号是必填字段，正文找不到说明标签不可信 |
| **长度在合理区间** | 3472 | **156** | 超长（历史邮件线程）/ 超短 |
| **精确去重后** | 3217 | **255** | 完全相同的正文（重复投递） |
| **近重复去重后** | 3000 | **217** | 同骨架+同公司+同型号（重复录入） |
| 加急标注自洽 | 3000 | 0 | `is_urgent=True` 但正文无加急措辞 |
| 无引用加急污染 | 3000 | 0 | 见下方说明 |
| token 长度合规 | 3000 | 0 | |

> **脏数据是刻意注入的**：真实原始数据从不干净。合成器按比例注入三类脏数据——
> 完全重复（6%）、近重复（9%）、超长邮件线程（6%）。
> 否则「去重」「长度过滤」只是写在代码里、从未被触发过的摆设。

### 3.3 严格切分

| 数据集 | 样本数 | 模板族 | 说明 |
| :--- | ---: | :--- | :--- |
| train | 1590 | 4 个分布内族 | |
| val | 120 | 同训练集 | |
| **test_iid** | 200 | 同训练集族，**骨架不重叠** | 考「会不会做」 |
| **test_ood** | 150 | **训练中完全未出现的 2 个族** | 考泛化 |

两重隔离（这是「严格隔离」的具体含义）：
1. **骨架隔离**——`skeleton_key`（子句模板 id 组合）分组切分，同骨架绝不跨集；
2. **模板族隔离**——`phone_transcript` / `quote_reply` 两族完全不进训练集，专做 OOD。

### 3.4 一个真实的数据缺陷（值得单独说）

早期版本的 `quote_reply` 模板硬编码了一句：

> 「（以下为对方原邮件）关于交期，我们希望越快越好」

它属于**被引用的历史邮件**，但模型无法区分「本次要求」与「历史引用」，
于是把 `is_urgent` 判为 `True`——而标注是 `False`。
**模型判对了，是标注错了。**

实测影响：OOD 集 150 条中 **18 条（12%）** 因此判错，全部由这一句造成。
修复后加了 `TestLabelTextConsistency` 测试钉住该不变量，并且**刻意保留**
「不着急」「别急着报」等否定表述——那是让模型判 `False` 的合理干扰项，
清掉会让 `is_urgent` 退化成关键词匹配。

## 四、8 GB 显存训 7B：三个关键优化

这是本项目技术含量最高的部分。**官方推荐写法在 8 GB 卡上跑不动**，原因如下。

### 4.1 问题定位

`prepare_model_for_kbit_training` 会把 `embed_tokens` 和 `lm_head` **升到 fp32**。
7B 的 `tie_word_embeddings=False`，两者都是 152064×3584 且**互不共享**：

| | fp16 | fp32 |
| :--- | ---: | ---: |
| embed_tokens | 1.02 GB | 2.04 GB |
| lm_head | 1.02 GB | 2.04 GB |
| **合计** | **2.04 GB** | **4.08 GB** |

实测常驻显存 **5.34 → 7.38 GiB**，训练峰值 **10.52 GiB**，
而物理显存仅 7.96 GiB（可用 6.87）。

> **最危险的是它不报 OOM**：WSL 允许显存超售，溢出到主机内存的表现是
> 「能跑，但 110 秒/步」。若不实测，很容易误以为成功。

### 4.2 三项优化

| # | 优化 | 效果 | 验证方式 |
| :--- | :--- | :--- | :--- |
| 1 | **不做 fp32 升级**（`fp32_upcast_non_quantized: false`） | 常驻 7.38 → **5.34 GiB** | 探针实测 |
| 2 | **只算答案位置 logits**（`logits_to_keep`） | 峰值 3.40 → **1.43 GiB**（0.5B 对照，降 58%） | loss 相对差 9.4e-08，**数学等价** |
| 3 | `bs=1` + 梯度累积 16 + 梯度检查点 + `paged_adamw_8bit` | 撑住 7B | 实测 |

**优化 2 的原理**：lm_head 输出是 `[batch, seq_len, vocab]`，Qwen vocab=151936。
`seq_len=832` 时仅 logits 就约 253 MB（bf16），loss 再 upcast fp32 翻倍——
而答案（目标 JSON）只有约 80 token，**90% 以上的 logits 算完即弃**。
这笔开销只与 `seq_len × vocab` 有关，**与模型大小无关**，7B 同样要付。

> **这里有个真实的坑**：右侧 padding 使答案不在序列末尾，
> 若照搬「labels 左移后取末尾 k 个」会**整体错位**——
> loss 照样下降、训练照样收敛，但学的是错位一环的标签。
> 正确公式是 `k = T - min(first_sup) + 1`，配 `padded[:, T-k+1:]`。
> 已写 4 个对齐测试钉死。

### 4.3 最终显存账

| 项 | 显存 |
| :--- | ---: |
| 4bit 量化线性层（65.3 亿权重 × 0.5 B/权重，实测反推） | 3.04 GB |
| embed_tokens（fp16，**不参与量化**） | 1.02 GB |
| lm_head（fp16，权重不共享 → **排除量化**） | 1.02 GB |
| 量化常数 + LoRA 权重 | ~0.26 GB |
| **常驻合计** | **5.34 GiB** |
| **训练峰值（含激活值）** | **6.04 GiB** |
| 可用显存 | 6.87 GiB |
| **余量** | **0.83 GiB** |

`max_seq_length` 定为 **832**：全量 2060 条样本实测最长 796 token，**100% 覆盖**，
比 1024 更省显存且不丢任何样本。

## 五、结果

完整表格见 [`RESULTS.md`](RESULTS.md)（由 `scripts/make_report.py` 自动生成）。

### 5.1 核心对比

| 模型 | 测试集 | 版本 | JSON 合法率 | Schema 合规率 | **全字段准确率** |
| :--- | :--- | :--- | ---: | ---: | ---: |
| Qwen2.5-1.5B | IID | 基座零样本 | 100.0% | 60.5% | **12.5%** |
| Qwen2.5-1.5B | IID | **微调后** | 100.0% | 100.0% | **87.5%** |
| Qwen2.5-1.5B | OOD | 基座零样本 | 100.0% | 70.7% | **7.3%** |
| Qwen2.5-1.5B | OOD | **微调后** | 100.0% | 99.3% | **80.7%** |
| Qwen2.5-7B | IID | 基座零样本 | 100.0% | 97.0% | **22.5%** |
| Qwen2.5-7B | IID | **微调后** | 100.0% | 100.0% | **93.0%** |
| Qwen2.5-7B | OOD | 基座零样本 | 100.0% | 93.3% | **15.3%** |
| Qwen2.5-7B | OOD | **微调后** | 100.0% | 100.0% | **91.3%** |

### 5.2 三个主要发现

**① 幻觉率被完全消除（最有价值的一项）**

7B 基座在「单价」上的**漏抽率高达 79.8%**——即把正文里明确给出的单价判成 null；
微调后降到 **0.0%**。客户名、数量、交付日期、付款条件、联系电话同样全部降到 0.0%。

> 基座的表现形态是「**宁可说不知道**」：JSON 格式完全正确（100%），
> 但大量字段填 null。全字段准确率只有 15.3% 就是这么来的。
> 微调同时解决了「不敢抽」和「抽错」两个问题。

**② 泛化差距随模型规模收窄**

| 模型 | IID | OOD（未见模板族） | 差距 |
| :--- | ---: | ---: | ---: |
| 1.5B | 87.5% | 80.7% | 6.8 pp |
| **7B** | **93.0%** | **91.3%** | **1.7 pp** |

7B 在**完全没有见过的两种文体**（电话记录整理稿、带历史引用的邮件回复）上
只掉 1.7 个百分点，说明它学到的是**抽取能力本身**，而不是记住了训练时的句式模板。
这正是 OOD 测试集存在的意义——如果只做随机切分，这个结论无法得出。

**③ 难点在语义，不在格式**

基座的 JSON 合法率已经是 100%（现代 Instruct 模型格式能力很强），
但全字段准确率仅 12.5%~22.5%。差距全部来自语义理解：

| 字段 | 1.5B 基座 → 微调 | 7B 基座 → 微调 | 难点 |
| :--- | ---: | ---: | :--- |
| 付款条件 | 53.0% → **100.0%** | 97.0% → 100% | 口语化表达归一到枚举 |
| 客户名称 | 71.5% → **100.0%** | 95.0% → 100% | 多方公司名消歧 |
| 交付日期 | 61.0% → **89.0%** | 66.0% → **95.0%** | 相对日期换算 |
| 单价 | 86.0% → 99.5% | **43.0% → 100.0%** | 只给总价时必须输出 null |

### 5.3 剩余短板（不掩饰）

7B 微调后在 OOD 上只剩两类错误，且都是**真实的能力短板**，不是数据噪声：

| 字段 | 错误率(IID/OOD) | 具体表现 |
| :--- | ---: | :--- |
| 交付日期 | 5.0% / 6.0% | 「发件日期 10/26，希望 72 天内交货」→ 标注 2026-01-06，模型答 2025-12-27，**跨月日期运算错约 12~20 天** |
| 数量 | 2.0% / 2.7% | 「1千件」→ 标注 1000，模型答 1500/1200，**中文数量词换算不稳，且受「上批 800 只」干扰** |

**这两项都不是微调能轻易解决的**：前者需要多步算术推理，后者需要更细的数值归一化训练信号。
如实记录比粉饰更有价值，也为后续改进指明了方向。

### 5.4 训练与推理成本

| 实验 | 方案 | 可训练参数 | 占比 | 峰值显存 | 训练耗时 | 最终 train loss |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: |
| Qwen2.5-1.5B | LoRA (bf16) | 18.5 M | 1.182% | 5.41 GiB | 32.7 min | 0.0123 |
| **Qwen2.5-7B** | **QLoRA (NF4)** | 40.4 M | **0.919%** | **7.16 GiB** | 108.1 min | 0.0008 |

> 7B 的峰值 7.16 GiB 出现在**完整训练**（含优化器步进与验证），
> 高于压测时的 6.04 GiB —— 因为压测只跑单步、未累积优化器状态。
> 这个数字更接近真实训练的开销，如实记录。

## 六、局限

- **训练数据是合成的**：分布与真实业务文本有差距，真实落地需少量真实样本做校准。
  但**基座与微调后的相对差异是可信的**——两者面对完全相同的输入。
- **只做 LoRA / QLoRA**，未做全参微调对比（8 GB 做不了 7B 全参）。
- **评测集同样是合成的**，指标绝对值不代表线上表现。
- **未做量化部署（GPTQ/AWQ）与推理加速（vLLM）对比**，属后续工作。
- **is_urgent 剩余误报**主要来自「不着急」类否定表述，属设计内的难点。

## 八、工程记录

本项目共 **20+ 次提交**，其中修复的真实缺陷（都是「不报错但结果错」那类）：

| 缺陷 | 后果 | 发现方式 |
| :--- | :--- | :--- |
| pandas 把 `None` 转成 `NaN` 写进 JSONL | 非法 JSON；`gold is None` 判断失效，**幻觉率假性恒等于 0** | 单元测试 |
| 脏数据注入误用 replace 而非 append | 去重规则从未触发，数据漏斗全是 0 | 观察漏斗异常 |
| 4bit 模型评测调用 `merge_and_unload()` | 反量化成 bf16（7B≈15GB），**必然 OOM** | 代码审查 |
| `logits_to_keep` 的 shift 对齐错位 | loss 照降但学错标签 | 端到端等价性验证 |
| `prepare_model_for_kbit_training` 的 fp32 升级 | 7B 峰值 10.52 GiB > 物理显存，靠超售硬撑（110 s/步） | 显存探针 |
| 引用段落含加急词 | `is_urgent` 标签噪声，OOD 误报 12% | 错误分析 |
| sweep 脚本时长单位混淆 | 低估训练时长约 8 倍 | 与进度条核对 |
| 编排脚本重复训练 | 误用 STAGE=all 导致 7B 重训（最贵的一步，1.8 小时） | 发现日志里在跑训练而非评测 |
| 训练成本表重复行 | 同一份指标因两个副本被列两次 | 阅读生成的报告 |

**性能结论的教训**：一度认为「实际训练比压测慢 2.1 倍」并怀疑分配器碎片化，
还实测了 `expandable_segments`（结果反而慢 15%）。最终发现压测脚本当时
**把 8 条样本编成 1 个 batch 计时、且预热未完成**，修正后基线是
4.03 s/micro-batch，与训练完全吻合（×16 梯度累积 = 64.5 s/step）。
**性能结论必须在无并发、预热充分的条件下测，否则会把噪声当成结论。**
